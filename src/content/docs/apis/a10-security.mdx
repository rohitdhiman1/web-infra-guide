Everything so far assumed a friendly caller. A real API has to answer two questions on every request: *who is this?* and *are they allowed to do this?* This module covers how APIs answer both, what can go wrong, and the vocabulary interviewers expect. OAuth 2.0, OIDC and SAML get their own deep dive later; here you learn where they fit.

## Authentication and authorisation

:::note[Definition]
**Authentication** (often “authn”) establishes **who** is calling: the caller proves an identity, usually by presenting a credential the server can check.

**Authorisation** (often “authz”) decides **what** that identity may do: which actions, on which resources. It always comes after authentication, and happens on every request.
:::

| | Authentication | Authorisation |
|---|---|---|
| Question | Who are you? | Are you allowed to do this? |
| Based on | A credential: API key, token, certificate | Rules: roles, scopes, ownership |
| Fails with | `401 Unauthorized` (despite the name) | `403 Forbidden`, or `404 Not Found` to hide a resource |
| Example | Alice's token is valid and unexpired | Alice may read *her* order, not Bob's |

## Concepts

<span id="concept-a10-1"></span>

### <span class="concept-badge">A10.1</span> Two checks, in order

Every protected request goes through the same layers. First **authentication**: is there a credential, and is it valid? Then **authorisation**, which itself has two levels. *Function-level*: may this kind of caller do this kind of action at all, for example refunds? *Object-level*: may this caller touch *this particular* order?

Most real breaches aren't broken passwords or cryptography. They're a missing authorisation check on one endpoint.

<Takeaway>
Authenticate once, then authorise every action and every object, on every request.
</Takeaway>

<span id="concept-a10-2"></span>

### <span class="concept-badge">A10.2</span> How callers prove who they are

| Credential | Typical caller | How it's sent | Watch out for |
|---|---|---|---|
| API key | A server or script belonging to a customer | `Authorization: Bearer sk_live_…` or a header like `X-API-Key` | Long-lived; identifies an *application*, not a person |
| Bearer token (often a JWT) | Apps acting for a user, or services | `Authorization: Bearer eyJ…` | Anyone holding it can use it, so keep it short-lived |
| Session cookie | A browser on your own website | `Cookie: session=…` | Needs CSRF protection, because browsers send cookies automatically |
| Client certificate (mTLS) | Service-to-service inside a company | During the TLS handshake ([5.15](/part-5-tls/#concept-5-15)) | Certificate issuing and rotation take real infrastructure |

Credentials go in **headers**, never in the URL. URLs end up in access logs, browser history, proxy logs and `Referer` headers.

<Takeaway>
Pick the credential for the caller (scripts, users, browsers or services), and always send it in a header.
</Takeaway>

<span id="concept-a10-3"></span>

### <span class="concept-badge">A10.3</span> 401, 403 and 404, done properly

**401 Unauthorized** means *not authenticated*: no credential, or one that's invalid or expired. It must carry `WWW-Authenticate` saying how to authenticate. For bearer tokens (RFC 6750) that's `WWW-Authenticate: Bearer`, plus `error="invalid_token"` when a token was sent but is bad, so the client knows to fetch a new one.

**403 Forbidden** means authenticated but not allowed: the caller is known, and the answer is no. Use **404** instead when even admitting the resource exists would leak information, for example Bob asking for Alice's order. (A1.9 introduced the codes; this is when to use each.)

<Takeaway>
401 asks the caller to authenticate (with WWW-Authenticate), 403 refuses a known caller, and 404 hides what they mustn't see.
</Takeaway>

<span id="concept-a10-4"></span>

### <span class="concept-badge">A10.4</span> API keys

An API key is a long random secret that identifies a client application. Generate at least 128 bits of randomness. Give it a recognisable prefix such as `sk_live_`, so secret scanners can spot leaked keys in code.

Show the key to the customer **once**, and store only a **hash** of it. Like a password, a leaked database then doesn't leak usable keys. Because the key is long and random, a plain SHA-256 is enough; slow password hashes aren't needed.

Let customers hold several keys, so they can rotate one without downtime. Attach scopes and rate limits to each key (A9).

<Takeaway>
Generate API keys with high entropy and a prefix, show them once, store them hashed, and make rotation easy.
</Takeaway>

<span id="concept-a10-5"></span>

### <span class="concept-badge">A10.5</span> Bearer tokens and JWTs

A *bearer* token works for whoever holds it, like cash. Many APIs use **JWTs** (JSON Web Tokens): three base64url parts separated by dots, a header, a payload of *claims*, and a signature.

| Part | Example | Meaning |
|---|---|---|
| Header | `{"alg": "RS256", "kid": "2026-10"}` | How it's signed, and with which key |
| Payload | `{"sub": "alice", "iss": "https://auth.example.com", "aud": "orders-api", "exp": 1793491200, "scope": "orders:read orders:write"}` | Who it's about, who issued it, who it's for, when it expires, what it allows |
| Signature | `MEUCIQ…` | Proves the issuer created exactly this header and payload |

A JWT is **signed, not encrypted**: anyone can decode the payload, so never put secrets in it. Before trusting one, verify:
- the **signature**, with the algorithm *you* expect (never `alg: none`, and never let the token choose);
- `exp` and `nbf`, so it isn't expired or not yet valid;
- `iss`, so it comes from your identity provider;
- `aud`, so it's meant for *this* API.

A JWT can't easily be revoked before it expires, so keep access tokens short-lived (minutes) and use refresh tokens to get new ones. The alternative is *opaque* tokens that the API checks with the issuer on every request (token introspection): easier to revoke, at the cost of an extra call.

<Takeaway>
A JWT is signed, not secret: verify the signature, expiry, issuer and audience, and keep it short-lived.
</Takeaway>

<span id="concept-a10-6"></span>

### <span class="concept-badge">A10.6</span> Where OAuth 2.0, OpenID Connect and SAML fit

**OAuth 2.0** is about *delegated authorisation*: how an application gets an access token to call an API, either for a user or for itself. The two flows to know are *authorization code with PKCE* (an app acting for a signed-in user) and *client credentials* (a service acting for itself). OAuth on its own doesn't tell the app who the user is.

**OpenID Connect (OIDC)** adds that: an *ID token* (a JWT) describing the signed-in user, on top of OAuth 2.0. It's what “Sign in with Google” uses.

**SAML** is the older, XML-based way enterprises do single sign-on between an identity provider (such as Okta or Azure AD) and applications. The later deep dive covers all three end to end.

<Takeaway>
OAuth 2.0 issues access tokens, OIDC adds who the user is, and SAML is enterprise single sign-on.
</Takeaway>

<span id="concept-a10-7"></span>

### <span class="concept-badge">A10.7</span> Authorisation models

| Model | The rule looks like | Example |
|---|---|---|
| Role-based (RBAC) | Roles grant permissions | Support agents may read any order |
| Scopes | The token lists what it may do | `refunds:write` is needed to refund |
| Attribute-based (ABAC) | Rules over attributes of the caller and the resource | Customers may change an order only if they own it and it's still pending |

Real APIs combine them. Whatever the model, the rules run **on the server, on every request**. Deny by default: an action that no rule allows is forbidden. Hiding a button in the UI is not authorisation.

<Takeaway>
Combine roles, scopes and ownership rules, enforce them on the server, and deny by default.
</Takeaway>

<span id="concept-a10-8"></span>

### <span class="concept-badge">A10.8</span> Object-level authorisation (BOLA)

The most common serious API flaw: the endpoint checks that you're logged in, but not that the object is yours. Bob changes `ord_7` to `ord_1` in the URL and reads Alice's order. OWASP ranks **broken object-level authorisation** as the #1 API risk.

Check ownership on **every** access to an object, in the query itself where you can: `SELECT … WHERE id = ? AND customer_id = ?`. Opaque, hard-to-guess ids help a little, but they aren't a defence: ids leak through logs, emails and shared links. Answer a failed ownership check with 404, so callers can't probe which ids exist.

<Takeaway>
Check that the caller may touch this specific object on every request; unguessable ids are not a substitute.
</Takeaway>

<span id="concept-a10-9"></span>

### <span class="concept-badge">A10.9</span> Function-level and property-level authorisation

**Function-level:** admin and support endpoints need their own checks. `GET /admin/orders` must not work just because someone guessed the path (OWASP's *broken function-level authorisation*).

**Property-level:** a caller may be allowed to touch an object but not every field of it. On input, ignore or reject fields the client doesn't own, such as `total` or `status: "paid"`. That's *mass assignment*, and the field-ownership rule from A0.9 is the defence. On output, don't return fields the caller shouldn't see, such as another customer's email in a list.

<Takeaway>
Authorise actions and fields as well as objects: guard admin endpoints, and only accept and return the fields this caller may use.
</Takeaway>

<span id="concept-a10-10"></span>

### <span class="concept-badge">A10.10</span> Transport and secrets

Serve the API over **HTTPS only**, and send HSTS ([5.13](/part-5-tls/#concept-5-13)) from any domain browsers use, so credentials never cross the network in clear text. Behind the gateway, use mTLS between services if the network isn't trusted (A9.8).

Keep secrets out of the repository: signing keys, database passwords and API keys belong in a secret store or the deployment environment. Never log `Authorization` headers or tokens. Plan for rotation before you need it: support two signing keys at once (the `kid` header picks one), and rotate API keys without downtime.

<Takeaway>
Encrypt every hop, keep secrets out of code and logs, and design rotation in from the start.
</Takeaway>

<span id="concept-a10-11"></span>

### <span class="concept-badge">A10.11</span> The OWASP API Security Top 10

OWASP's list of the most common API security risks (2023 edition) makes a good checklist. Most entries map to something in this track:

| Risk | What goes wrong | Where this track covers it |
|---|---|---|
| API1 Broken object-level authorisation | Reading or changing someone else's object | A10.8 |
| API2 Broken authentication | Weak, leaked or unchecked credentials and tokens | A10.2–A10.5 |
| API3 Broken object property-level authorisation | Mass assignment; exposing fields | A10.9, A0.9 |
| API4 Unrestricted resource consumption | No limits on requests, page sizes or payloads | A9, A5.1 |
| API5 Broken function-level authorisation | Admin endpoints open to everyone | A10.9 |
| API6 Unrestricted access to sensitive business flows | Bots abusing checkout, sign-up or coupons | Rate limits (A9) plus business rules |
| API7 Server-side request forgery | Your server fetches a URL an attacker chose | A7.9 |
| API8 Security misconfiguration | Open CORS, verbose errors, missing TLS | A9.7, A2.6, A10.10 |
| API9 Improper inventory management | Forgotten old versions and test hosts | A6.8 |
| API10 Unsafe consumption of APIs | Trusting third-party APIs blindly | Validate their responses; timeouts (A3.2) |

<Takeaway>
Use the OWASP API Top 10 as a review checklist for every API you design.
</Takeaway>

## Lab A10 — tokens, keys, scopes and ownership

Two orders, `ord_1` (Alice's) and `ord_2` (Bob's), in memory. Two kinds of caller. **Users** get a short-lived JWT from `POST /token`, a stand-in for an identity provider such as Keycloak, Auth0 or Entra ID so the lab runs offline. It skips the part where a real provider checks a password or passkey, and just signs a token for the user name you send. **Services** send an API key, and the server stores only its SHA-256 hash.

Authentication runs before routing, for every path except `/token` and `/.well-known/jwks.json`, so a new endpoint is protected until someone opens it up on purpose. Authorisation lives in the handlers, because only they know which order is being touched.

#### Callers

| Caller | Credential | Role | Scopes |
|---|---|---|---|
| `alice`, `bob` | JWT | customer | `orders:read orders:write` |
| `sam` | JWT | support | `orders:read orders:read:any` |
| `ana` | JWT | admin | `orders:read orders:read:any orders:write refunds:write` |
| warehouse service | `X-API-Key: wh_test_4f9c2a7d1e8b6035` (a throwaway value) | service | `orders:read orders:read:any` |

Tokens are ES256, signed with a P-256 key generated at startup, and carry `iss: https://id.orders.test`, `aud: orders-api`, `sub`, `exp` (5 minutes), `jti`, `scope` and `role`.

#### Spec

| # | Request | Must return |
|---|---|---|
| 1 | `GET /orders/ord_1` with no credential | `401` problem, type `unauthenticated`, `WWW-Authenticate: Bearer realm="orders-api"` |
| 2 | `GET /no-such-thing` with no credential | `401`, not `404`: unknown paths reveal nothing either |
| 3 | `POST /token` `{"user": "alice"}` / `{"user": "mallory"}` | `200` with `access_token`, `token_type: Bearer`, `expires_in: 300` and `Cache-Control: no-store` / `400` |
| 4 | A token whose `exp` passed 10 minutes ago | `401` problem, type `invalid-token`, `WWW-Authenticate` containing `error="invalid_token"` |
| 5 | A valid signature but `iss: https://evil.test`, or `aud: billing-api` | `401` |
| 6 | Bob's token with its payload swapped for Alice's, or `"alg": "none"` with no signature | `401` |
| 7 | `X-API-Key: wh_test_guessed` | `401`, `WWW-Authenticate: ApiKey realm="orders-api"` |

| 10 | Bob: `GET /orders/ord_1`, and `PATCH` it | `404`, word for word the same as `GET /orders/ord_999` |

| 16 | Alice: `DELETE /orders/ord_1` | `405` with `Allow` listing `GET` and `PATCH` |

#### Verifying a token

The verifier accepts exactly one algorithm. A verifier that believes the token's own `alg` header can be handed `"alg": "none"`, or an HS256 token signed with the public key as if it were a shared secret.

<TabItem label="Java (Spring Boot)">

Spring Security does the authentication. `ApiKeyFilter` runs just before the bearer-token filter and handles `X-API-Key`.

```java
@Bean
SecurityFilterChain api(HttpSecurity http, AuthenticationEntryPoint entryPoint) throws Exception {
  return http
      // No cookies and no sessions: every request carries its own credential, so CSRF doesn't apply.
      .csrf(c -> c.disable())
      .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
      .authorizeHttpRequests(a -> a
          .requestMatchers("/token", "/.well-known/jwks.json", "/error").permitAll()
          .anyRequest().authenticated())   // deny by default
      .oauth2ResourceServer(o -> o.jwt(j -> {}).authenticationEntryPoint(entryPoint))
      .exceptionHandling(e -> e.authenticationEntryPoint(entryPoint))
      .addFilterBefore(new ApiKeyFilter(entryPoint), BearerTokenAuthenticationFilter.class)
      .build();
}

@Bean
JwtDecoder jwtDecoder(SigningKeys keys, @Value("${auth.issuer}") String issuer,
                      @Value("${auth.audience}") String audience) {
  // In production: NimbusJwtDecoder.withIssuerLocation(issuer), which fetches and caches the provider's JWKS.
  NimbusJwtDecoder decoder = NimbusJwtDecoder.withJwkSource(new ImmutableJWKSet<>(keys.publicJwks()))
      .jwsAlgorithm(SignatureAlgorithm.ES256).build();
  decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
      new JwtTimestampValidator(Duration.ofSeconds(30)),   // exp and nbf, with 30 s of clock skew
      new JwtIssuerValidator(issuer),
      new JwtClaimValidator<List<String>>(JwtClaimNames.AUD, aud -> aud != null && aud.contains(audience))));
  return decoder;
}
```

PyJWT does the verifying. A middleware runs it before routing, so nothing reaches a route unauthenticated.

```python
def authenticate(authorization: str | None, api_key: str | None) -> Caller:
    if api_key is not None:
        client = API_KEYS.get(sha256(api_key))          # only hashes are stored
        if client is None:
            raise Unauthenticated("invalid-token", "unknown API key", 'ApiKey realm="orders-api"')
        return Caller(client[0], "service", client[1])
    scheme, _, token = (authorization or "").partition(" ")
    if scheme.lower() != "bearer" or not token:
        raise Unauthenticated("unauthenticated", "send Authorization: Bearer <token>, or X-API-Key",
                              'Bearer realm="orders-api"')
    try:
        claims = jwt.decode(token, PUBLIC_KEY, algorithms=["ES256"], audience=AUDIENCE, issuer=ISSUER,
                            leeway=30, options={"require": ["exp", "iss", "aud", "sub"]})
    except jwt.InvalidTokenError:
        raise Unauthenticated("invalid-token", "the access token is invalid or expired",
                              'Bearer realm="orders-api", error="invalid_token"') from None
    return Caller(claims["sub"], claims.get("role"), frozenset(claims.get("scope", "").split()))


@app.middleware("http")
async def authenticate_requests(request: Request, call_next):
    if request.url.path in PUBLIC_PATHS:
        return await call_next(request)
    try:
        request.state.caller = authenticate(request.headers.get("authorization"), request.headers.get("x-api-key"))
    except Unauthenticated as e:
        return problem(request, 401, e.type, e.detail, headers={"WWW-Authenticate": e.challenge})
    return await call_next(request)
```

#### Checking scope and ownership

Every handler starts the same way: the scope check (403), then the ownership check (404), then the work. Both languages put the caller in one small `Caller` type, so handlers never touch a raw token or key.

<Tabs syncKey="lab-lang">
<TabItem label="Java (Spring Boot)">

```java
// Caller: function-level authorisation
void require(String scope) {
  if (!has(scope)) {
    throw new ApiException(HttpStatus.FORBIDDEN, "insufficient-scope", "this needs the " + scope + " scope",
        Map.of(), Map.of("WWW-Authenticate", "Bearer error=\"insufficient_scope\", scope=\"" + scope + "\""));
  }
}

// OrderController: object-level authorisation. Missing and "not yours" are the same 404.
private Order find(Caller c, String id, boolean write) {
  Order o = orders.get(id);
  boolean mayAccess = o != null && (o.customerId().equals(c.id())
      || (write ? "admin".equals(c.role()) : c.has("orders:read:any")));
  if (!mayAccess) {
    throw new ApiException(HttpStatus.NOT_FOUND, "order-not-found", "order " + id + " not found");
  }
  return o;
}

@GetMapping("/orders/{id}")
Order get(@PathVariable String id, Authentication auth) {
  Caller c = Caller.from(auth);
  c.require("orders:read");
  return find(c, id, false);
}
```

# Caller: function-level authorisation
def require(self, scope: str) -> None:
    if not self.has(scope):
        raise ApiError(403, "insufficient-scope", f"this needs the {scope} scope",
                       headers={"WWW-Authenticate": f'Bearer error="insufficient_scope", scope="{scope}"'})


# Object-level authorisation. Missing and "not yours" are the same 404.
def find(c: Caller, order_id: str, write: bool) -> Order:
    o = ORDERS.get(order_id)
    may_access = o is not None and (o.customerId == c.id or (c.role == "admin" if write else c.has("orders:read:any")))
    if not may_access:
        raise ApiError(404, "order-not-found", f"order {order_id} not found")
    return o


@app.get("/orders/{order_id}")
def get_order(order_id: str, request: Request):
    c = request.state.caller
    c.require("orders:read")
    return asdict(find(c, order_id, write=False))
