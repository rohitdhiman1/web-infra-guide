Every method makes a promise, and every status code tells the client what to do next. Clients, proxies, caches and retry libraries all act on those promises without knowing anything about your API. Get them right and the whole HTTP ecosystem works for you; get them wrong and a retry creates a duplicate order or a cache serves stale data. Part 3 introduced [methods (3.2)](/part-3-http11/#concept-3-2) and [status codes (3.3)](/part-3-http11/#concept-3-3); this module is about choosing them when you design an API.

## Concepts

<span id="concept-a1-1"></span>

### <span class="concept-badge">A1.1</span> Safe, idempotent, cacheable

Three properties decide what clients, proxies and caches may do with a request:

- **Safe:** the client asked for no change (GET, HEAD, OPTIONS).
- **Idempotent:** sending the same request twice leaves the server in the same state as sending it once (all safe methods, plus PUT and DELETE).
- **Cacheable:** a response may be stored and reused (GET and HEAD in practice).

Idempotency is about the **effect on server state**, not the response: a second DELETE can return 404 and still be idempotent. These properties are why a proxy may retry a GET after a dropped connection, but must never blindly retry a POST.

| Method | Safe | Idempotent | Typical use in this API |
|---|---|---|---|
| GET | yes | yes | Read an order or the collection |
| HEAD | yes | yes | Same as GET, headers only |
| OPTIONS | yes | yes | Ask what's allowed (and CORS preflight, [3.15](/part-3-http11/#concept-3-15)) |
| POST | no | **no** | Create an order; any action that doesn't fit the others |
| PUT | no | yes | Replace an order's client fields completely |
| PATCH | no | not by definition | Change some fields of an order |
| DELETE | no | yes | Remove an order |

<Takeaway>
Idempotency is about the effect on the server, not the response; it's what tells clients and proxies what they may repeat.
</Takeaway>

<span id="concept-a1-2"></span>

### <span class="concept-badge">A1.2</span> POST creates, and isn't idempotent

`POST /orders` asks the collection to create a new member; the server picks the id. Answer `201 Created` with a `Location` header pointing at the new resource.

Two identical POSTs create two orders. That's correct behaviour, and also the root of the duplicate-payment problem that idempotency keys solve in module A3.

<Takeaway>
POST to a collection creates a new member: answer 201 with Location, and expect duplicates if it's retried.
</Takeaway>

<span id="concept-a1-3"></span>

### <span class="concept-badge">A1.3</span> PUT replaces

`PUT /orders/ord_1` sends the *complete* new state of everything the client owns. Leave a field out and it's missing, not unchanged, so the strict answer is 422.

Because the result is fully described by the request, PUT is idempotent: send it ten times, get the same order. PUT can also *create* when the client chooses the id (`PUT /carts/my-cart-id`). This API uses server-chosen ids, so PUT to an unknown order is 404.

<Takeaway>
PUT sends the complete new state, so sending it twice changes nothing more.
</Takeaway>

<span id="concept-a1-4"></span>

### <span class="concept-badge">A1.4</span> PATCH changes part of a resource

PATCH sends a description of a change, and its `Content-Type` says which description language. **JSON Merge Patch** (RFC 7396, `application/merge-patch+json`) looks like the resource: `{"customer": "x@example.com"}` changes one field, and `null` means “remove this field”.

**JSON Patch** (RFC 6902, `application/json-patch+json`) is a list of operations like `{"op": "add", "path": "/items/-", ...}`. Merge Patch is simpler and covers most needs; JSON Patch can do things Merge Patch can't, such as appending to an array. PATCH isn't idempotent *by definition*: Merge Patch usually is, but JSON Patch's “append an item” isn't.

If you don't support a patch format, answer 415 and list the ones you do in `Accept-Patch`.

<Takeaway>
PATCH sends a change, and its Content-Type names the patch format; Merge Patch covers most needs.
</Takeaway>

<span id="concept-a1-5"></span>

### <span class="concept-badge">A1.5</span> DELETE

Removes the resource. Answer `204 No Content`.

A repeated DELETE finds nothing; this API answers 404, and some APIs answer 204 again so retries look identical. Both are defensible. Pick one and document it.

<Takeaway>
DELETE answers 204; choose whether a repeat gives 404 or 204, and document it.
</Takeaway>

<span id="concept-a1-6"></span>

### <span class="concept-badge">A1.6</span> GET must never change anything

Browsers prefetch links, crawlers follow them, monitoring tools poll them, and proxies retry them. A `GET /orders/ord_1/cancel` *will* get called by something that didn't mean it.

Support **HEAD** for every GET (same headers, no body): monitoring and link checkers use it.

<Takeaway>
If a request changes anything, it isn't a GET.
</Takeaway>

<span id="concept-a1-7"></span>

### <span class="concept-badge">A1.7</span> Status codes in classes

The first digit is the contract: 2xx “it worked”, 3xx “look elsewhere”, 4xx “you (the client) need to change something”, 5xx “we failed; the same request may work later”. Clients must handle any code by its class even if they don't know it, so a sensible client treats an unfamiliar 418 like a 400.

The **reason phrase** after the number is decoration: clients must ignore it, Tomcat leaves it out entirely, and HTTP/2 doesn't have one.

<Takeaway>
Clients act on the first digit; the reason phrase is decoration.
</Takeaway>

<span id="concept-a1-8"></span>

### <span class="concept-badge">A1.8</span> 400 vs 422

400 Bad Request: the server can't even parse the request, such as broken JSON. 422 Unprocessable Content: it parsed fine but breaks the rules, like a quantity of 0, a missing customer or a quantity sent as `"two"`. RFC 9110 made 422 part of core HTTP in 2022 (it used to be WebDAV-only), and its name changed from “Unprocessable Entity”.

Some APIs use 400 for everything; separating them tells the client whether to fix its JSON serializer or its data.

<Takeaway>
400 means it didn't parse; 422 means it parsed but breaks the rules.
</Takeaway>

<span id="concept-a1-9"></span>

### <span class="concept-badge">A1.9</span> 401 vs 403 vs 404

401 Unauthorized actually means *unauthenticated*: no valid credentials, and the response must carry `WWW-Authenticate` saying how to authenticate. 403 Forbidden: the server knows who you are, and the answer is still no. When even confirming that a resource exists would leak information (someone else's order), answer 404 instead.

[Module A10](/apis/a10-security/) covers authentication and authorisation properly; for now, know which code means what.

<Takeaway>
401 is “who are you?”, 403 is “no”, and 404 is “no, and I won't say it exists”.
</Takeaway>

<span id="concept-a1-10"></span>

### <span class="concept-badge">A1.10</span> 404 vs 405 vs 410

404: nothing at this URL. 405 Method Not Allowed: the resource exists but not for this method, and the response **must** include `Allow` listing what does work. 410 Gone: it existed and was removed on purpose, so clients may forget the URL; rarely worth the bookkeeping.

<Takeaway>
A 405 without an Allow header is incomplete.
</Takeaway>

<span id="concept-a1-11"></span>

### <span class="concept-badge">A1.11</span> 406 vs 415

Both are about formats, in opposite directions. 406 Not Acceptable: the client's `Accept` header rules out every format you can *produce*. 415 Unsupported Media Type: the request's `Content-Type` is a format you can't *consume*. Many APIs ignore `Accept` and always send JSON. That's common, but being strict catches client bugs early.

<Takeaway>
406 is about what you produce (Accept); 415 is about what you consume (Content-Type).
</Takeaway>

<span id="concept-a1-12"></span>

### <span class="concept-badge">A1.12</span> 409 vs 412 vs 422

422: the request is invalid on its own. 409 Conflict: the request is valid but clashes with the resource's *current state*, such as editing an order that's already cancelled. 412 Precondition Failed: the client made the request conditional (“only if it's still version 7”, with `If-Match`) and the condition is false.

That's the cure for lost updates in module A4.

<Takeaway>
Invalid on its own is 422; wrong for the current state is 409; a failed If-Match is 412.
</Takeaway>

<span id="concept-a1-13"></span>

### <span class="concept-badge">A1.13</span> Choosing the 2xx

Every success code tells the client something different:

| Code | Meaning | What comes with it |
|---|---|---|
| 200 OK | Here's the result | The result in the body |
| 201 Created | A new resource exists | `Location` with its URL, usually the resource in the body |
| 202 Accepted | Received; you'll do it later | Somewhere to check progress (module A7) |
| 204 No Content | Done, nothing to say | No body at all |

<Takeaway>
Pick the 2xx that tells the client what happened: 200, 201, 202 or 204.
</Takeaway>

<span id="concept-a1-14"></span>

### <span class="concept-badge">A1.14</span> 5xx means “not your fault”

500 is what happens when your code throws; never send it on purpose for a client mistake, because clients and load balancers treat 5xx as a reason to retry or fail over. 503 Service Unavailable: overloaded or in maintenance, ideally with `Retry-After`. 502 and 504 come from a proxy in front of you ([3.4](/part-3-http11/#concept-3-4)).

<Takeaway>
5xx means the same request may work later, so never use it for a client's mistake.
</Takeaway>

<span id="concept-a1-15"></span>

### <span class="concept-badge">A1.15</span> The headers an API must get right

Several status codes are incomplete without a header:

| Header | Send it with | Why |
|---|---|---|
| `Content-Type` | Every body | Says what format the body is in |
| `Location` | 201 | Where the new resource lives |
| `Allow` | 405 | Which methods do work |
| `Accept-Patch` | 415 on a PATCH | Which patch formats you take |
| `Retry-After` | 429 and 503 | When to try again |
| `WWW-Authenticate` | 401 | How to authenticate |

Later modules add `ETag` and `If-Match` (A4), `Idempotency-Key` (A3), `Cache-Control` (A4) and request ids (A9).

<Takeaway>
Each status code has a header that completes it: Location, Allow, Retry-After, WWW-Authenticate.
</Takeaway>

<span id="concept-a1-16"></span>

### <span class="concept-badge">A1.16</span> Make state changes safe to repeat

A client whose “cancel” request timed out doesn't know whether it worked, so it sends it again. If the second cancel returns 409 (“already cancelled”), the client sees an error for something that succeeded.

Treat a request that would leave the resource exactly as it is as a no-op success (200). Reserve 409 for changes that would *actually* change a resource that can't change. This is the same idea A3 generalises to POST.

<Takeaway>
A request that would change nothing should succeed, not fail, so retries are safe.
</Takeaway>

## Lab A1 — the full method set

Extend the A0 API. Add PUT, PATCH and DELETE, and make every response code deliberate. The client may set `customer`, `currency`, `items` and `status` (only `pending` or `cancelled`). A cancelled order is final.

#### Spec

Each row is one test. Both reference implementations pass all of them.

| # | Request | Must return |
|---|---|---|
| 1 | `POST /orders`, valid JSON | `201`, `Location: /orders/ord_N` |
| 2 | The same POST twice | Two different `Location`s (POST isn't idempotent) |
| 3 | `POST /orders`, body `{"customer": ` | `400`: not valid JSON |
| 4 | `POST /orders`, `"quantity": "two"` | `422`: JSON of the wrong shape |
| 5 | `POST /orders`, empty customer, `"currency": "euro"`, no items | `422` with a `fields` object naming `customer`, `currency` and `items` |
| 6 | `POST /orders` with `Content-Type: text/plain` | `415` |
| 7 | `GET /orders/ord_1` with `Accept: application/xml` | `406` |
| 8 | `DELETE /orders` | `405` with `Allow` including `GET` and `POST` |
| 9 | `HEAD /orders/ord_1` | `200`, headers, empty body |
| 10 | `PUT /orders/ord_1` with all four fields, sent twice | `200` both times, identical bodies, recomputed `total` |
| 11 | `PUT /orders/ord_1` with only `customer` | `422` (PUT replaces everything) |
| 12 | `PUT /orders/ord_999999` | `404` (ids are server-chosen) |
| 13 | `PATCH /orders/ord_1` with `Content-Type: application/json` | `415` with `Accept-Patch: application/merge-patch+json` |
| 14 | `PATCH` merge patch `{"customer": "x@example.com"}` | `200`; customer changed, items untouched |
| 15 | `PATCH` merge patch `{"customer": null}` | `422`: a required field can't be removed |
| 16 | `PATCH {"status": "cancelled"}` twice, then `PATCH {"customer": "y@…"}` | `200`, `200`, then `409` |
| 17 | `DELETE /orders/ord_1`, then again, then `GET` | `204` with no body, then `404`, then `404` |

Error bodies stay simple in this module: `{"error": "...", "fields": {...}}`. Module A2 replaces them with the RFC 9457 standard format.

#### Mapping errors to codes in one place

Handlers throw; one handler turns failures into responses. The interesting part is telling 400 from 422.

```java
@RestControllerAdvice
public class ApiErrors {

  @ExceptionHandler(ApiException.class)
  ResponseEntity<Map<String, Object>> api(ApiException e) {
    return body(e.status, e.getMessage(), e.fields);
  }

  /** 400 if the bytes aren't JSON at all; 422 if it's JSON of the wrong shape. */
  @ExceptionHandler(HttpMessageNotReadableException.class)
  ResponseEntity<Map<String, Object>> unreadable(HttpMessageNotReadableException e) {
    if (e.getCause() instanceof StreamReadException || e.getCause() == null) {   // Jackson 3: tools.jackson.core.exc
      return body(HttpStatus.BAD_REQUEST, "request body is not valid JSON", Map.of());
    }
    return body(HttpStatus.UNPROCESSABLE_CONTENT, "request body has the wrong shape", Map.of());
  }

  @ExceptionHandler(HttpMediaTypeNotSupportedException.class)
  ResponseEntity<Map<String, Object>> mediaType(HttpMediaTypeNotSupportedException e) {
    // Spring fills in Accept (and Accept-Patch for PATCH): tell the client what would work.
    return ResponseEntity.status(HttpStatus.UNSUPPORTED_MEDIA_TYPE).headers(e.getHeaders())
        .body(Map.of("error", "send Content-Type: " + e.getSupportedMediaTypes().getFirst()));
  }
}
```

```python
async def validation_handler(_: Request, e: RequestValidationError) -> JSONResponse:
    """400 if the body isn't JSON (or is missing); 422 if it's JSON of the wrong shape."""
    errors = e.errors()
    if any(err["type"] == "json_invalid" or (err["type"] == "missing" and tuple(err["loc"]) == ("body",))
           for err in errors):
        return JSONResponse({"error": "request body is not valid JSON"}, status_code=400)
    fields = {".".join(str(x) for x in err["loc"][1:]) or "body": err["msg"] for err in errors}
    return JSONResponse({"error": "request body has the wrong shape", "fields": fields}, status_code=422)

app.add_exception_handler(RequestValidationError, validation_handler)
```

FastAPI's default is 422 for both cases, so broken JSON needs this remapping to become a 400.

#### PUT, PATCH and the safe-to-repeat rule (A1.16)

<Tabs syncKey="lab-lang">
<TabItem label="Java (Spring Boot)">

```java
// PUT: replace every client-settable field. Idempotent.
@PutMapping(path = "/{id}", consumes = MediaType.APPLICATION_JSON_VALUE)
public Order replace(@PathVariable String id, @RequestBody OrderInput body) {
  Order current = existing(id);                       // 404 if unknown
  var problems = body.problems(true);                 // every field required
  if (!problems.isEmpty()) throw new ApiException(HttpStatus.UNPROCESSABLE_CONTENT, "validation failed", problems);
  return apply(current, body);
}

// PATCH with JSON Merge Patch. Declaring consumes makes Spring answer 415 + Accept-Patch otherwise.
@PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
public Order patch(@PathVariable String id, @RequestBody String raw) {
  Order current = existing(id);
  Map<String, Object> patch = json.readValue(raw, Map.class);
  // ...reject null for required fields (422), then merge:
  Map<String, Object> base = json.convertValue(current.input(), Map.class);
  base.putAll(patch);
  OrderInput merged = json.convertValue(base, OrderInput.class);
  // ...validate merged (422), then:
  return apply(current, merged);
}

/** A cancelled order is final, but repeating the same change is a no-op 200. */
private Order apply(Order current, OrderInput next) {
  if (next.equals(current.input())) return current;
  if (current.status().equals("cancelled")) {
    throw new ApiException(HttpStatus.CONFLICT, "order " + current.id() + " is cancelled and can't be changed");
  }
  Order updated = Order.from(current.id(), next, next.status(), current.createdAt());
  store.save(updated);
  return updated;
}
```

```python
    merged = current.input().model_dump(by_alias=True) | {k: v for k, v in patch.items() if k in CLIENT_FIELDS}
```

## What the frameworks do for you, and what they don't

Building the same spec in both frameworks shows how much HTTP behaviour comes from defaults. Know these when someone asks why your API returns a particular code.

| Behaviour | Spring Boot 4 | FastAPI |
|---|---|---|
| HEAD for every GET | Automatic | **Not automatic**: list `HEAD` in the route's methods |
| 405 with `Allow` | Automatic and complete | Sent, but `Allow` lists only the **first** route on that path (from Starlette), so `DELETE /orders` said `Allow: GET` instead of `GET, POST`. The lab adds a handler that collects every route's methods |
| 406 for an unacceptable `Accept` | Automatic (with `produces`), and the body is empty: it can't send JSON to a client that refused JSON | Not checked: add a dependency |
| 415 for a wrong `Content-Type` | Automatic (with `consumes`), including `Accept-Patch` for PATCH | Not checked: add a dependency |
| Broken JSON | 400 | 422, unless you remap it |
| Unknown JSON fields | Ignored | Ignored |
| Reason phrase | Omitted (`HTTP/1.1 201`) | Sent (`HTTP/1.1 201 Created`) |
| Header name case | `Location`, `Allow` | `location`, `allow` (header names are case-insensitive, so both are correct) |

#### Try it with curl

```bash
curl -i -X DELETE localhost:8080/orders                       # 405 + Allow
curl -i localhost:8080/orders/ord_1 -H 'Accept: application/xml'    # 406
curl -I localhost:8080/orders/ord_1                           # HEAD
curl -i -X PATCH localhost:8080/orders/ord_1 \
  -H 'Content-Type: application/json' -d '{"status":"cancelled"}'    # 415 + Accept-Patch
curl -i -X PATCH localhost:8080/orders/ord_1 \
  -H 'Content-Type: application/merge-patch+json' -d '{"status":"cancelled"}'   # 200, twice
```
