“Why REST and not gRPC?” is a favourite interview question because there's no single right answer, only trade-offs. This module compares the styles you'll meet by what actually crosses the wire, and builds one of them, a Server-Sent Events stream, since it's the one that stays inside plain HTTP.

**Concepts**

- **<a id="concept-a8-1" class="concept-num" href="#concept-a8-1">A8.1</a> Resource-oriented HTTP (“REST”).** Resources at URLs, standard methods and status codes, usually JSON (modules A0–A7). Its strength is that everything in between understands it: browsers, curl, caches, CDNs, proxies, log tools. Its weaknesses: clients may need several calls to assemble a screen (*under-fetching*) or get fields they don't need (*over-fetching*), and there's no streaming.
- **<a id="concept-a8-2" class="concept-num" href="#concept-a8-2">A8.2</a> RPC and gRPC.** RPC models calls as functions (`GetOrder(id)`) rather than resources. gRPC is the common modern form: a `.proto` file defines services and messages, code generators produce typed clients and servers, and calls travel as **Protobuf** (compact binary) over **HTTP/2** ([Part 6](/part-6-http2-http3/)), always as `POST /package.Service/Method`. The status goes in an HTTP/2 *trailer* (`grpc-status`), so HTTP's status codes and caching mostly don't apply. It's great inside a company: small messages, deadlines that propagate, streaming in both directions, strict contracts. It's poor at the edge: browsers can't speak it directly and you can't debug it with curl.
- **<a id="concept-a8-3" class="concept-num" href="#concept-a8-3">A8.3</a> GraphQL.** One endpoint and a typed schema; the client sends a query naming exactly the fields it wants, across related objects, in one round trip. It solves over- and under-fetching when many clients need different shapes of the same data graph. The costs: HTTP caching mostly stops working (every query is a POST to `/graphql`); errors often come back as `200` with an `errors` array; one innocent-looking nested query can make thousands of database calls (the N+1 problem, eased with batching *dataloaders*); and servers must limit query depth and cost.
- **<a id="concept-a8-4" class="concept-num" href="#concept-a8-4">A8.4</a> Server-Sent Events.** One long-lived HTTP response with `Content-Type: text/event-stream`, to which the server keeps appending `id:`, `event:` and `data:` lines, each event ending with a blank line. Browsers support it natively (`EventSource`) and **reconnect automatically**, sending `Last-Event-ID` so the server can replay what was missed. It's one-way (server to client), but it's still plain HTTP, so authentication, proxies and load balancers work unchanged. Under HTTP/1.1 each open stream holds a connection, and browsers allow only about 6 per host; HTTP/2 multiplexing removes that limit.
- **<a id="concept-a8-5" class="concept-num" href="#concept-a8-5">A8.5</a> WebSockets.** An HTTP request with `Upgrade: websocket` gets `101 Switching Protocols`, after which the TCP connection carries WebSocket frames in both directions, and HTTP is gone. Use them when traffic is genuinely two-way and latency-sensitive: chat, collaborative editing, multiplayer. You give up HTTP semantics on that connection: no status codes, no per-message headers. Request ids, errors, reconnection and auth refresh become your problem. Load balancers need sticky, long-lived connections, and deploys must drain them.
- **<a id="concept-a8-6" class="concept-num" href="#concept-a8-6">A8.6</a> Webhooks and message brokers.** Webhooks (A7) push events to another company's HTTP server. Inside your own systems, a broker such as Kafka does the same job better: durable, replayable, ordered per partition, and consumers read at their own pace. A common shape is a broker inside the company, with webhooks or SSE at the edge for outsiders.
- **<a id="concept-a8-7" class="concept-num" href="#concept-a8-7">A8.7</a> Long-lived connections and operations.** Streams and sockets change how you run servers. Idle connections get cut by proxies, so send heartbeats (SSE comment lines such as `: keep-alive`) more often than the shortest idle timeout on the path. nginx buffers responses by default, so turn buffering off for streams (`X-Accel-Buffering: no` or `proxy_buffering off`, [Part 8](/part-8-reverse-proxy/)). Graceful shutdown waits for open requests, and a stream never finishes on its own: the lab's first Java version took 96 seconds to stop until it closed its streams first.
- **<a id="concept-a8-8" class="concept-num" href="#concept-a8-8">A8.8</a> Choosing.** For a public or partner API, use resource-oriented HTTP with OpenAPI. For internal service-to-service calls with strict contracts and high volume, gRPC. For many front-ends over a rich data graph, GraphQL, if you can invest in its operational guardrails. For live updates to clients, SSE (one-way) or WebSockets (two-way). For telling other companies something happened, webhooks; for telling your own services, a broker. Mixing is normal: many companies run gRPC inside and REST at the edge, translated by a gateway.

## Lab A8 — a resumable event stream

Every new order publishes an `order.created` event to an append-only log. `GET /orders/events` streams the log as Server-Sent Events, and a client that reconnects with `Last-Event-ID` gets everything it missed. Storage is in memory.

**Spec**

| # | Request | Must return |
|---|---|---|
| 1 | `GET /orders/events` (`Accept: text/event-stream`) | `200`, `Content-Type: text/event-stream`, connection stays open |
| 2 | While connected, create two orders | Two events: `id` 1 and 2, `event: order.created`, `data` with the order's JSON |
| 3 | Three orders exist; connect with `Last-Event-ID: 1` | Events 2 and 3 are replayed at once, then live events follow |
| 4 | Stay connected with no new orders | Comment lines (`: keep-alive`) arrive at the heartbeat interval |
| 5 | Stop the server while streams are open | It shuts down promptly, not after a timeout |

```java
@GetMapping(path = "/orders/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestHeader(name = "Last-Event-ID", required = false) String lastEventId) {
  long after = lastEventId != null && lastEventId.matches("\\d{1,18}") ? Long.parseLong(lastEventId) : 0;
  return events.subscribe(after);
}

// OrderEvents
public synchronized SseEmitter subscribe(long lastEventId) {
  SseEmitter emitter = new SseEmitter(0L);                     // no server-side timeout
  for (Event e : log) if (e.id() > lastEventId) send(emitter, e);   // replay what was missed
  streams.add(emitter);                                        // then follow live events
  emitter.onCompletion(() -> streams.remove(emitter));
  return emitter;
}

private void send(SseEmitter s, Event e) throws IOException {
  s.send(SseEmitter.event().id(String.valueOf(e.id())).name(e.type()).data(e.data()).reconnectTime(3000));
}
```

Requirement 5 needed a fix: Spring's graceful shutdown waits for in-flight requests, and an open stream never ends by itself. `OrderEvents` implements `SmartLifecycle` with the highest phase, so it completes every stream *before* the web server starts waiting. The tests went from 96 s to 2 s.

<TabItem label="Python (FastAPI)">

```python
@app.get("/orders/events")
async def order_events(request: Request):
    raw = request.headers.get("last-event-id", "")
    after = int(raw) if raw.isdigit() else 0

    async def stream():
        queue: asyncio.Queue = asyncio.Queue()
        STREAMS.add(queue)
        try:
            for event in LOG:                       # first replay what the client missed...
                if event["id"] > after:
                    yield frame(event)
            while True:                             # ...then follow live events
                try:
                    event = await asyncio.wait_for(queue.get(), HEARTBEAT_SECONDS)
                    yield frame(event)
                except TimeoutError:
                    yield ": keep-alive\n\n"        # keeps proxies from closing an idle stream
        finally:
            STREAMS.discard(queue)

    return StreamingResponse(stream(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})


def frame(event: dict) -> str:
    return f"id: {event['id']}\nevent: {event['type']}\nretry: 3000\ndata: {json.dumps(event['data'])}\n\n"
```

Uvicorn also waits for open responses on shutdown, so run it with `--timeout-graceful-shutdown 5`.

## You've got it when

For a given client and use case you can pick REST, gRPC, GraphQL, SSE, WebSockets or webhooks and defend the choice with the trade-offs: caching, browser support, contracts, streaming, operations. You can also describe exactly what each one sends over the wire.
