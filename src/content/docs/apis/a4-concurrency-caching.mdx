Two clients edit the same order and one change silently disappears. A client downloads the same unchanged order every few seconds. Both problems have the same fix: give every version of a resource a name, the **ETag**, and let clients make requests *conditional* on it. This module covers the conditional headers from RFC 9110 and the parts of HTTP caching ([3.11](/part-3-http11/#concept-3-11), RFC 9111) that matter for APIs.

## Concepts

<span id="concept-a4-1"></span>

### <span class="concept-badge">A4.1</span> The lost update

Two clients read version 1, both change it, both write. The second write is based on stale data and overwrites the first, and both get 200.

Nothing errors and nothing is logged; the data is just wrong. HTTP is stateless, so the server can't know what a client saw unless the client says so.

<Takeaway>
Without preconditions, the last writer silently wins and earlier changes vanish.
</Takeaway>

<span id="concept-a4-2"></span>

### <span class="concept-badge">A4.2</span> Pessimistic or optimistic

*Pessimistic* concurrency locks the record while someone edits it. That doesn't fit HTTP: a user can open an edit form and walk away, holding the lock indefinitely.

*Optimistic* concurrency lets everyone read freely and checks for conflicts at write time: “save only if it's still the version I read”. Conflicts are rare, so retrying the occasional one costs less than locking every time.

<Takeaway>
Over HTTP, detect conflicts when writing instead of locking while people think.
</Takeaway>

<span id="concept-a4-3"></span>

### <span class="concept-badge">A4.3</span> ETags

An `ETag` header names the current version of a representation: `ETag: "7"`. It's opaque to clients; they store it and send it back, never parse it.

Common ways to generate one are a version column bumped on every write (as in the lab) or a hash of the response body. A *strong* ETag (`"7"`) means byte-for-byte identical. A *weak* one (`W/"7"`) means semantically equivalent, such as the same data compressed differently.

Writes require strong ETags.

<Takeaway>
An ETag names one version of a representation; clients store it and send it back.
</Takeaway>

<span id="concept-a4-4"></span>

### <span class="concept-badge">A4.4</span> If-Match makes writes conditional

`PATCH` with `If-Match: "7"` means “apply this only if the current ETag is still "7"”. If it isn't, the server answers **412 Precondition Failed** and changes nothing.

The client then re-reads and decides: reapply its change, merge, or ask the user. `If-Match: *` means “only if it exists at all”. Its opposite, `If-None-Match: *` on a PUT, means “only if it *doesn't* exist yet”, a safe create-only PUT.

<Takeaway>
If-Match makes a write conditional on the version you read; a mismatch is 412.
</Takeaway>

<span id="concept-a4-5"></span>

### <span class="concept-badge">A4.5</span> 428 forces the habit

A client that never sends `If-Match` can still overwrite blindly. **428 Precondition Required** (RFC 6585) lets the server insist: writes without a precondition are refused. Use it on resources where lost updates matter, which for orders is all of them.

<Takeaway>
428 makes clients send If-Match, so a blind overwrite can't happen.
</Takeaway>

<span id="concept-a4-6"></span>

### <span class="concept-badge">A4.6</span> The check must be atomic

Comparing `If-Match` with the version you just read, then writing, is a race: another write can land in between. Do the comparison inside the write: `UPDATE orders SET …, version = version + 1 WHERE id = ? AND version = ?`.

Zero rows updated means someone else won, so answer 412. The lab's concurrency test fires two writes at once and checks that exactly one wins.

<Takeaway>
Compare the version inside the UPDATE, not before it.
</Takeaway>

<span id="concept-a4-7"></span>

### <span class="concept-badge">A4.7</span> Conditional GET and 304

A client that already has version `"7"` sends `If-None-Match: "7"`. If nothing changed, the server answers **304 Not Modified** with no body, and the client reuses its copy.

This saves bandwidth and parsing, not necessarily server work: the server still has to find the current ETag, so make that cheap. The older pair, `Last-Modified` and `If-Modified-Since`, only has one-second resolution; prefer ETags.

<Takeaway>
If-None-Match lets an unchanged resource answer 304 with no body.
</Takeaway>

<span id="concept-a4-8"></span>

### <span class="concept-badge">A4.8</span> Cache-Control for APIs

The directives that matter for APIs:

| Directive | Means | Use it for |
|---|---|---|
| `no-store` | Don't keep a copy at all | Secrets, one-time data |
| `no-cache` | Keep a copy, but revalidate before every use | Personal data that changes. With ETags it becomes cheap 304s |
| `max-age=60` | Fresh for 60 seconds; no need to ask | Data that can be a little stale |
| `private` | Only the user's own client may store it | Anything about one user |
| `public` | Shared caches and CDNs may store it too | Reference data that's the same for everyone |

Despite its name, `no-cache` doesn't mean “don't cache”. The lab sends `private, no-cache` for orders: personal data, always checked.

<Takeaway>
no-store, no-cache, max-age, private and public each say something different: choose deliberately.
</Takeaway>

<span id="concept-a4-9"></span>

### <span class="concept-badge">A4.9</span> Shared caches and personal data

A CDN or proxy that caches one customer's order and serves it to another is a data breach. By default a shared cache must not store a response to a request that carried `Authorization`, unless the response explicitly allows it with a directive such as `public` or `s-maxage`.

Mark personal responses `private` anyway. Cache shared reference data, such as a product catalogue, with `public, max-age=…`.

<Takeaway>
Personal data is private; only shared reference data is public.
</Takeaway>

<span id="concept-a4-10"></span>

### <span class="concept-badge">A4.10</span> Vary

If a response depends on a request header, say so with `Vary`. A response that changes with `Accept` or `Accept-Language` must carry `Vary: Accept` or `Vary: Accept-Language`, or a cache will serve the JSON version to a client that asked for CSV. Caches use those headers as part of the cache key.

<Takeaway>
If the response depends on a request header, name that header in Vary.
</Takeaway>

## Lab A4 — ETags and conditional requests

This lab focuses on the order resource: create, read and PATCH (JSON Merge Patch, as in A1) with versions. Payments from A3 aren't part of it. Each lab from here on uses its own Postgres schema (`a4`, `a5`, …) in the same container, so their tables never clash.

#### Spec

| # | Request | Must return |
|---|---|---|
| 1 | `POST /orders` | `201` with `ETag: "1"` |
| 2 | `GET /orders/ord_1` | `200`, `ETag: "1"`, `Cache-Control` containing `private` and `no-cache`; the body has no `version` field |
| 3 | `GET` with `If-None-Match: "1"` | `304`, empty body, `ETag: "1"` |
| 4 | `GET` with `If-None-Match: "0"` | `200` with the body |
| 5 | `PATCH` without `If-Match` | `428`, type `…/precondition-required` |
| 6 | `PATCH` with `If-Match: "1"` | `200`, `ETag: "2"` |
| 7 | Alice PATCHes with `"1"`, then Bob PATCHes with `"1"` | Alice `200`; Bob `412`; the order keeps Alice's change |
| 8 | Two PATCHes with `If-Match: "1"` sent at the same moment | Exactly one `200` and one `412`; the ETag ends at `"2"` |
| 9 | `PATCH` with `If-Match: *` | `200` |

@GetMapping("/{id}")
public ResponseEntity<Order> get(@PathVariable String id,
                                 @RequestHeader(name = "If-None-Match", required = false) String ifNoneMatch) {
  Order order = existing(id);
  if (matches(ifNoneMatch, order.etag())) {
    return ResponseEntity.status(HttpStatus.NOT_MODIFIED).eTag(order.etag()).cacheControl(REVALIDATE).build();
  }
  return ResponseEntity.ok().eTag(order.etag()).cacheControl(REVALIDATE).body(order);
}

@PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
public ResponseEntity<Order> patch(@PathVariable String id,
                                   @RequestHeader(name = "If-Match", required = false) String ifMatch,
                                   @RequestBody String raw) {
  Order current = existing(id);
  if (ifMatch == null) throw new ApiException(HttpStatus.PRECONDITION_REQUIRED, "precondition-required", "...");
  if (!matches(ifMatch, current.etag())) throw new ApiException(HttpStatus.PRECONDITION_FAILED, "precondition-failed", "...");
  OrderInput merged = merge(current, raw);
  // Re-check inside the UPDATE: another writer may have slipped in since we read `current`.
  if (!orders.updateIfVersion(Ids.order(id), current.version(), merged)) {
    throw new ApiException(HttpStatus.PRECONDITION_FAILED, "precondition-failed", "...");
  }
  Order updated = existing(id);
  return ResponseEntity.ok().eTag(updated.etag()).cacheControl(REVALIDATE).body(updated);
}

#### Try it

```bash
curl -i localhost:8080/orders/ord_1                                  # note the ETag
curl -i localhost:8080/orders/ord_1 -H 'If-None-Match: "1"'          # 304
curl -i -X PATCH localhost:8080/orders/ord_1 -H 'Content-Type: application/merge-patch+json' \
  -d '{"customer":"x@example.com"}'                                   # 428
curl -i -X PATCH localhost:8080/orders/ord_1 -H 'Content-Type: application/merge-patch+json' \
  -H 'If-Match: "1"' -d '{"customer":"x@example.com"}'               # 200, ETag "2"
```
