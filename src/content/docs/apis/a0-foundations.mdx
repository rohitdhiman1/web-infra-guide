Before methods and status codes, get the vocabulary straight. Most confusion in API discussions, and most interview follow-ups that go wrong, come from fuzzy answers to “what is a resource?” or “is this actually REST?”. This module makes those answers precise.

**Concepts**

- **<a id="concept-a0-1" class="concept-num" href="#concept-a0-1">A0.1</a> What an API is.** An application programming interface is a contract between two programs: what one may ask, what it must send, and what it gets back. An *HTTP API* is a contract carried by HTTP requests and responses. The contract is the product. The code behind it can be rewritten, but every client depends on the contract, so changing it is expensive (module A6).
- **<a id="concept-a0-2" class="concept-num" href="#concept-a0-2">A0.2</a> Resources and identifiers.** A *resource* is anything worth naming: an order, the collection of all orders, a customer's open orders. A URL *identifies* a resource; it isn't the resource. `/orders` names the collection and `/orders/ord_1` names one order in it. Good identifiers are stable: the same URL keeps pointing to the same thing.
- **<a id="concept-a0-3" class="concept-num" href="#concept-a0-3">A0.3</a> Representations.** What travels over the wire is a *representation* of the resource's current state, such as a JSON document, never the resource itself. One resource can have several representations (JSON, CSV, a PDF invoice), and the client picks with `Accept` ([content negotiation, 3.10](/part-3-http11/#concept-3-10)). This is the R in REST: *representational* state transfer.
- **<a id="concept-a0-4" class="concept-num" href="#concept-a0-4">A0.4</a> Nouns and verbs.** In a resource-oriented API, URLs are nouns and HTTP methods are the verbs: `POST /orders`, not `POST /createOrder`. The payoff is a *uniform interface*: every client, proxy and cache already knows what GET, PUT and DELETE promise ([3.2](/part-3-http11/#concept-3-2)), so they can retry, cache and log correctly without knowing your API. Some operations don't map to a noun cleanly (“recalculate shipping”). Modelling them as an action sub-resource, `POST /orders/ord_1/recalculation`, is a common and acceptable compromise. Be able to say why you chose it.
- **<a id="concept-a0-5" class="concept-num" href="#concept-a0-5">A0.5</a> What REST actually is.** REST is an architectural style that Roy Fielding described in his 2000 dissertation as a set of constraints: client-server, stateless, cacheable, a uniform interface, a layered system, and optionally code on demand. The uniform interface includes *hypermedia*: responses carry links that tell the client what it can do next. Very few “REST APIs” follow that last part. Most are better described as **resource-oriented HTTP+JSON APIs**. Saying exactly that in an interview, and knowing why hypermedia is rarely used (clients are written against documentation anyway), is a stronger answer than claiming your API is RESTful.
- **<a id="concept-a0-6" class="concept-num" href="#concept-a0-6">A0.6</a> The maturity ladder.** Leonard Richardson's model is a handy way to place an API. Level 0: one URL, everything is a POST (like old SOAP or JSON-RPC over HTTP). Level 1: separate resources. Level 2: resources plus proper methods and status codes. Level 3: hypermedia. Most good public APIs sit at level 2, which is where this track aims.
- **<a id="concept-a0-7" class="concept-num" href="#concept-a0-7">A0.7</a> Statelessness.** Each request carries everything the server needs to handle it, including who the caller is (usually a token in a header). The server keeps no conversation state between requests. *Resource* state, like the orders in a database, is fine; *session* state, like “the order this user is currently editing” kept in one server's memory, isn't. Statelessness is what lets a load balancer send each request to any server ([Part 9](/part-9-load-balancing/)) and lets you add servers to scale.
- **<a id="concept-a0-8" class="concept-num" href="#concept-a0-8">A0.8</a> JSON on the wire.** JSON has only strings, numbers, booleans, null, arrays and objects, so you decide the rest by convention. Four that matter: **money** as an integer of minor units (`1500` means €15.00) with its currency, because floats can't represent most decimal amounts exactly; **timestamps** as ISO 8601 in UTC (`2026-10-31T22:22:17Z`); **one naming style** everywhere (this track uses camelCase); and **null versus absent** treated as different things, which matters for PATCH (module A1).
- **<a id="concept-a0-9" class="concept-num" href="#concept-a0-9">A0.9</a> Who owns which field.** The contract says which fields a client may set and which the server owns. In this track a client sends the customer, currency and items; the server decides the `id`, the `total`, the starting `status` and `createdAt`. A server that accepts a client's `total` will eventually sell something for €0.
- **<a id="concept-a0-10" class="concept-num" href="#concept-a0-10">A0.10</a> Wrap collections in an object.** Return `{"data": [...]}`, not a bare `[...]`. An object can grow new fields later, such as a link to the next page (module A5), without breaking clients. A bare array can't.

## Lab A0 — the first three endpoints

Build the smallest useful orders API. Orders live in memory; data disappears when the process stops, which is fine until module A3.

**Spec**

| Request | Must return |
|---|---|
| `POST /orders` with a JSON order | `201 Created`, a `Location` header like `/orders/ord_1`, and the order in the body with server-set `id`, `total`, `status: "pending"` and `createdAt` |
| `GET /orders/ord_1` | `200 OK` with the order as `application/json` |
| `GET /orders/ord_999999` | `404 Not Found` with a JSON body containing an `error` string |
| `GET /orders` | `200 OK` with `{"data": [ ...orders ]}` |

The order representation:

```json
{
  "id": "ord_1",
  "customer": "ada@example.com",
  "currency": "EUR",
  "items": [{ "sku": "BOOK-42", "quantity": 2, "unitPrice": 1500 }],
  "total": 3000,
  "status": "pending",
  "createdAt": "2026-10-31T22:22:17Z"
}
```

**The create endpoint**

<Tabs syncKey="lab-lang">
<TabItem label="Java (Spring Boot)">

```java
@RestController
@RequestMapping("/orders")
public class OrderController {
  private final OrderStore store;

  public OrderController(OrderStore store) {
    this.store = store;
  }

  @PostMapping
  public ResponseEntity<Order> create(@RequestBody NewOrder body) {
    Order order = store.create(body);   // server sets id, total, status, createdAt
    return ResponseEntity
        .created(URI.create("/orders/" + order.id()))   // 201 + Location
        .body(order);
  }

  @GetMapping
  public Map<String, List<Order>> list() {
    return Map.of("data", store.all());   // wrapped, not a bare array
  }
}
```

Money and the server-owned fields live in the record:

```java
public record Order(String id, String customer, String currency, List<OrderItem> items,
                    long total, String status, Instant createdAt) {
  public record OrderItem(String sku, int quantity, long unitPrice) {}   // unitPrice in cents
}
```

</TabItem>

```python
@app.post("/orders", status_code=201, response_model=Order)
def create_order(body: NewOrder, response: Response) -> Order:
    order = store.create(body)   # server sets id, total, status, createdAt
    response.headers["Location"] = f"/orders/{order.id}"
    return order


@app.get("/orders", response_model=OrderList)
def list_orders() -> OrderList:
```

**Try it with curl**

Run your server, then watch the raw exchange. `-i` prints the response headers; `-v` also shows what curl sent.

```bash
curl -i -X POST localhost:8080/orders \
  -H 'Content-Type: application/json' \
  -d '{"customer":"ada@example.com","currency":"EUR",
       "items":[{"sku":"BOOK-42","quantity":2,"unitPrice":1500}]}'

curl -i localhost:8080/orders/ord_1
curl -i localhost:8080/orders/ord_999999
```

Things to notice:

- The Spring Boot (Tomcat) server answers `HTTP/1.1 201`, with nothing after the code. The reason phrase is optional, and clients ignore it.
- Spring sends the body with `Transfer-Encoding: chunked` rather than `Content-Length` ([chunked encoding, 3.7](/part-3-http11/#concept-3-7)). Both are valid ways to frame a body.
- Try sending a `total` of 1 in the POST body. The response still says 3000.

## You've got it when

You can explain, without notes, the difference between a resource, its identifier and its representation; say honestly whether a given API is “RESTful” and what level it reaches; and justify each field-ownership and JSON decision in the order representation above.
