Some concerns apply to every endpoint: limiting how much each client may call, tracing a request across services, letting the right browser apps in, and terminating TLS. They belong in one place, an **API gateway** (or a shared middleware layer), not copied into every handler. This module covers what that layer does, and builds three of its jobs into the orders API.

## Concepts

<span id="concept-a9-1"></span>

### <span class="concept-badge">A9.1</span> What a gateway does

An API gateway is a reverse proxy ([Part 8](/part-8-reverse-proxy/)) specialised for APIs: TLS termination, authentication ([A10](/apis/a10-security/)), rate limits and quotas, request ids and logging, CORS, routing by path or version, request-size limits, and sometimes translation (REST outside, gRPC inside).

Examples: nginx or Envoy with configuration, Kong, AWS API Gateway, or a framework middleware stack. The rule: anything every endpoint needs, and that doesn't depend on business logic, belongs there.

<Takeaway>
Anything every endpoint needs, and that isn't business logic, belongs in the gateway.
</Takeaway>

<span id="concept-a9-2"></span>

### <span class="concept-badge">A9.2</span> Why rate limit

To protect the service from overload and abuse, to share capacity fairly between clients (one runaway script shouldn't hurt everyone), and to enforce paid tiers. Limit per *client identity* (API key, user, account), falling back to IP address only when there's no identity.

Behind a proxy the remote address is the proxy itself, so trust `X-Forwarded-For` only when your own proxy set it ([3.16](/part-3-http11/#concept-3-16)).

<Takeaway>
Rate limits protect capacity and fairness; key them on a client identity.
</Takeaway>

<span id="concept-a9-3"></span>

### <span class="concept-badge">A9.3</span> The algorithms

| Algorithm | How it works | Strength | Weakness |
|---|---|---|---|
| Fixed window | Count per calendar second or minute | Simple | Allows twice the limit across a boundary |
| Sliding window | Count over the last N seconds | Exact with a log of timestamps; cheap if you blend two window counts | The exact version stores every timestamp |
| Token bucket | Tokens refill at a steady rate up to a capacity; each request spends one | Bursts up to the capacity, a steady average. What most APIs use | Needs two numbers per client |
| Leaky bucket | Requests queue and leave at a steady rate | Smooth traffic | Adds delay. This is nginx's `limit_req` ([Part 10](/part-10-caching-security/)) |

<Takeaway>
Token bucket is the usual choice: bursts up to a capacity, a steady average rate.
</Takeaway>

<span id="concept-a9-4"></span>

### <span class="concept-badge">A9.4</span> Saying no well

Refuse with **429 Too Many Requests**, a `Retry-After` header, and a problem body (A2), and tell well-behaved clients their budget *before* they hit it: the lab sends `X-RateLimit-Limit` and `X-RateLimit-Remaining` on every response. These `X-` headers are a common convention, not a standard.

An IETF draft is standardising the information as `RateLimit` and `RateLimit-Policy` fields, so check what your gateway emits. Good clients slow down when the budget runs low, and back off with jitter after a 429 (A3).

<Takeaway>
Refuse with 429 and Retry-After, and show the remaining budget before it runs out.
</Takeaway>

<span id="concept-a9-5"></span>

### <span class="concept-badge">A9.5</span> Distributed limits

A limiter in each server's memory multiplies the limit by the number of servers behind the load balancer. Shared limits need shared state, usually Redis, updated atomically (a Lua script or `INCR` with expiry), or a limiter in the gateway that all traffic passes through.

A shared store adds latency and a dependency to every request, so decide what happens when it's down: *fail open* (allow, and risk overload) or *fail closed* (reject, and cause an outage). Most choose fail open with a local fallback limit.

<Takeaway>
In-memory limits multiply with instances; shared limits need a shared store and a failure policy.
</Takeaway>

<span id="concept-a9-6"></span>

### <span class="concept-badge">A9.6</span> Request ids

Give every request an id at the edge, return it in a header (`X-Request-Id`), put it in every log line and every error body, and forward it to every downstream call. A user who reports “error, request id abc-123” then leads you straight to the logs on every service it touched.

Accept a caller's id only if it matches a strict pattern: it ends up in your logs, so unvalidated input there is a log-injection risk. The W3C *Trace Context* standard (`traceparent` header) does the same job for distributed tracing systems such as OpenTelemetry ([Part 12](/part-12-observability/)).

<Takeaway>
One request id, everywhere: in the response, the logs, the errors and downstream calls.
</Takeaway>

<span id="concept-a9-7"></span>

### <span class="concept-badge">A9.7</span> CORS for APIs

Browsers block JavaScript on one origin from reading responses from another, unless the server allows it with CORS headers ([3.15](/part-3-http11/#concept-3-15)). For a request that isn't “simple”

(JSON bodies, custom headers like `X-API-Key`), the browser first sends a **preflight** `OPTIONS` asking permission, and only sends the real request if the answer allows that origin, method and those headers. List exact origins, never reflect whatever `Origin` arrives (especially with credentials), use `Access-Control-Max-Age` to cache preflights, and `Access-Control-Expose-Headers` for headers your JavaScript must read.

CORS protects *users* from malicious websites. It doesn't protect your API from curl or servers; that's what auth and rate limits are for.

<Takeaway>
CORS protects users from other websites; it doesn't protect your API from servers.
</Takeaway>

<span id="concept-a9-8"></span>

### <span class="concept-badge">A9.8</span> TLS at the edge and behind it

The gateway usually terminates the client's TLS connection ([5.14](/part-5-tls/#concept-5-14)). Behind it, the traffic either continues in plain HTTP on a trusted network, or is re-encrypted, often as **mutual TLS** ([5.15](/part-5-tls/#concept-5-15)) so each service can prove its identity to the next.

A service mesh such as Istio or Linkerd automates that mTLS between services. Whatever the gateway learned about the client (verified identity, original IP, protocol) has to travel inward in headers that the backend trusts *only* from the gateway.

<Takeaway>
TLS usually ends at the gateway; re-encrypt or use mTLS behind it if the network isn't trusted.
</Takeaway>

<span id="concept-a9-9"></span>

### <span class="concept-badge">A9.9</span> Other edge limits

Maximum body size (413, [Part 8](/part-8-reverse-proxy/)), maximum header size (431), request timeouts (408, or 504 from a proxy), and connection limits. Each one stops a whole class of abuse cheaply, before it reaches your application code.

<Takeaway>
Cheap limits at the edge stop whole classes of abuse before they reach your code.
</Takeaway>

## Lab A9 — request ids, rate limits, CORS

The endpoints are deliberately trivial (`GET /orders` returns an empty list, `GET /orders/{id}` returns 404). The work is in the layer around them: filters in Spring, middleware in FastAPI. Order matters. Request ids go outermost, so even a 429 or a CORS rejection carries an id, and CORS preflights never reach the rate limiter.

#### Spec

(token bucket: capacity 5, refill 1 per second, per `X-API-Key`)

| # | Request | Must return |
|---|---|---|
| 1 | Any request without `X-Request-Id` | A generated UUID in the `X-Request-Id` response header |
| 2 | With `X-Request-Id: abc-123` / with `X-Request-Id: bad id; DROP TABLE` | Echoed / replaced with a new id |
| 3 | `GET /orders/ord_9` with `X-Request-Id: trace-me-42` | `404` problem with `"requestId": "trace-me-42"` |
| 4 | 6 quick requests with one API key | `200` × 5 with `X-RateLimit-Remaining` 4, 3, 2, 1, 0; then `429` problem with `Retry-After: 1` |
| 5 | Exhaust key A, then call with key B | Key B gets `200`: limits are per client |
| 6 | Exhaust a key, wait 1.1 s, call again | `200`: the bucket refilled |
| 7 | Preflight from `https://shop.example.com` for POST with `content-type, x-api-key` | `200` with `Access-Control-Allow-Origin: https://shop.example.com`, POST allowed, `x-api-key` allowed, `Access-Control-Max-Age: 600` |
| 8 | Preflight from `https://evil.example` | No `Access-Control-Allow-Origin` (Spring answers 403, Starlette 400; browsers only look at the missing header) |
| 9 | `GET /orders` with `Origin: https://shop.example.com` | `Access-Control-Allow-Origin` set and `Access-Control-Expose-Headers` including `X-Request-Id` |

```java
final class TokenBucket {
  synchronized Decision take(long nowNanos) {
    tokens = Math.min(capacity, tokens + (nowNanos - lastNanos) / 1e9 * ratePerSecond);   // refill
    lastNanos = nowNanos;
    if (tokens >= 1) {
      tokens -= 1;
      return new Decision(true, (int) Math.floor(tokens), 0);
    }
    long wait = (long) Math.ceil((1 - tokens) / ratePerSecond);   // seconds until one whole token
    return new Decision(false, 0, Math.max(1, wait));
  }
}
```

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)              // outermost: runs before everything else
public class RequestIdFilter extends OncePerRequestFilter {
  static final Pattern SAFE = Pattern.compile("[A-Za-z0-9._-]{1,64}");

  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) ... {
    String incoming = req.getHeader("X-Request-Id");
    String id = incoming != null && SAFE.matcher(incoming).matches() ? incoming : UUID.randomUUID().toString();
    req.setAttribute("requestId", id);
    res.setHeader("X-Request-Id", id);
    MDC.put("requestId", id);                   // every log line on this thread now carries it
    try { chain.doFilter(req, res); } finally { MDC.remove("requestId"); }
  }
}
```

@app.middleware("http")
async def rate_limit(request: Request, call_next):
    if request.method == "OPTIONS":
        return await call_next(request)                       # preflights are free
    key = request.headers.get("x-api-key")
    client = f"key:{key}" if key else f"ip:{request.client.host}"
    allowed, remaining, retry_after = BUCKETS.setdefault(client, TokenBucket(CAPACITY, RATE)).take()
    limits = {"X-RateLimit-Limit": str(CAPACITY), "X-RateLimit-Remaining": str(remaining)}
    if not allowed:
        return problem(request, 429, "rate-limited", "...", headers=limits | {"Retry-After": str(retry_after)})
    response = await call_next(request)
    response.headers.update(limits)
    return response

app.add_middleware(CORSMiddleware, allow_origins=["https://shop.example.com"], allow_methods=["GET", "POST"],

@app.middleware("http")                                       # added last, so runs first
async def request_id(request: Request, call_next):
    incoming = request.headers.get("x-request-id", "")
    request.state.request_id = incoming if SAFE_ID.fullmatch(incoming) else str(uuid.uuid4())
    response = await call_next(request)
    response.headers["X-Request-Id"] = request.state.request_id
    return response
