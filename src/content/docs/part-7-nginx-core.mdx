This is where everything from Parts 1 to 6 becomes configuration. Most nginx confusion comes from three things: how a request picks a `server`, how it picks a `location`, and how directives inherit. Master those and the rest is reference lookup. Plan two weeks.

## Concepts

<span id="concept-7-1"></span>

### <span class="concept-badge">7.1</span> Architecture

One master process (reads config, binds ports, manages workers) and N worker processes, each an event loop. `worker_processes auto;` gives one per CPU core; `worker_connections` caps connections per worker.

<span id="concept-7-2"></span>

### <span class="concept-badge">7.2</span> Open source vs nginx Plus

F5 sells nginx Plus with extras like active health checks, a live API dashboard and `least_time` balancing. Learn the open-source version first, and note when a guide assumes Plus.

<span id="concept-7-3"></span>

### <span class="concept-badge">7.3</span> Config structure

Contexts nest: `main` → `events` and `http` → `server` → `location`. There are also `stream` (raw TCP/UDP) and `mail` contexts.

<span id="concept-7-4"></span>

### <span class="concept-badge">7.4</span> Directive inheritance

Values flow down from outer contexts. The trap: array directives like `add_header` and `proxy_set_header` are *replaced*, not merged, if you set any at an inner level.

<span id="concept-7-5"></span>

### <span class="concept-badge">7.5</span> Server selection

nginx first matches `listen` (IP and port), then `server_name` from the Host header or SNI. Order: exact name, leading wildcard, trailing wildcard, regex, then `default_server`.

<span id="concept-7-6"></span>

### <span class="concept-badge">7.6</span> Location matching

`=` exact match wins immediately. Otherwise nginx finds the longest prefix; `^~` on it stops the search.

Then regexes (`~` and `~*`) are tried in file order, and the first match wins. Else the longest prefix is used.

<span id="concept-7-7"></span>

### <span class="concept-badge">7.7</span> root vs alias

`root` appends the full URI to the path; `alias` replaces the matched location part. Mixing them up is a top cause of 404s.

<span id="concept-7-8"></span>

### <span class="concept-badge">7.8</span> try\_files

Check files in order, then fall back, for example `try_files $uri $uri/ /index.html;` for single-page apps.

<span id="concept-7-9"></span>

### <span class="concept-badge">7.9</span> index and autoindex

Which file serves a directory request, and whether to list directory contents.

<span id="concept-7-10"></span>

### <span class="concept-badge">7.10</span> Variables

`$host`, `$uri`, `$request_uri`, `$args`, `$remote_addr`, `$scheme` and more. `map` builds new variables from old ones and is the clean way to do conditional logic.

<span id="concept-7-11"></span>

### <span class="concept-badge">7.11</span> rewrite and return

`return 301 https://$host$request_uri;` for redirects. `rewrite` changes the URI with regexes. Prefer `return` when you can.

<span id="concept-7-12"></span>

### <span class="concept-badge">7.12</span> "If is evil."

`if` inside `location` behaves in surprising ways. Use `map`, `try_files` or separate locations instead.

<span id="concept-7-13"></span>

### <span class="concept-badge">7.13</span> MIME types and default\_type

The `types` block maps extensions to `Content-Type`.

<span id="concept-7-14"></span>

### <span class="concept-badge">7.14</span> Request processing phases

nginx handles each request in ordered phases: rewrite, access, try\_files, content, log. Knowing them explains why directive order in the file often doesn't matter.

<span id="concept-7-15"></span>

### <span class="concept-badge">7.15</span> Modules

Core functionality is split into modules, some compiled in and some dynamic. `nginx -V` shows what your build includes.

<span id="concept-7-16"></span>

### <span class="concept-badge">7.16</span> Safe operations

`nginx -t` to test, `nginx -T` to dump the full config, `nginx -s reload` for a zero-downtime reload. Reload starts new workers and drains old ones gracefully.

## In the sandbox

1. Install nginx from the official nginx.org repo (newer than the distro package). Read every line of the default config.
2. Host two sites on one VM with two `server_name` values. Test with `curl -H 'Host: a.test' http://<ip>/`.
3. Write ten `location` blocks mixing `=`, `^~`, prefix and regex. Predict which one answers each of twenty URLs, then check by returning a different text from each one.
4. Reproduce the `root` vs `alias` bug on purpose, and fix it.
5. Deploy a single-page app build with `try_files` and long cache headers on hashed assets.
6. During a `wrk` load test, run `nginx -s reload` and confirm zero failed requests.
