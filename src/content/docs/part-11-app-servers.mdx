This answers your original question about frameworks. Django and Flask are not web servers. Their `runserver` and `flask run` commands are development servers, never for production. A real deployment is nginx → an application server → your framework code. Plan one week.

## Concepts

<span id="concept-11-1"></span>

### <span class="concept-badge">11.1</span> Why the layers exist

nginx handles slow clients, TLS, static files and buffering. The app server manages Python processes. The framework only turns a request into a response.

<span id="concept-11-2"></span>

### <span class="concept-badge">11.2</span> WSGI

Python's synchronous interface (PEP 3333): the server calls `app(environ, start_response)` once per request. Flask and classic Django use it.

<span id="concept-11-3"></span>

### <span class="concept-badge">11.3</span> ASGI

The async successor. `async def app(scope, receive, send)` supports WebSockets, long-lived connections and many concurrent requests per process. FastAPI, Starlette and modern Django use it.

<span id="concept-11-4"></span>

### <span class="concept-badge">11.4</span> Gunicorn

A pre-fork WSGI server (the model from [4.7](/part-4-raw-servers/#concept-4-7)). Tune `--workers` (a common start is 2 × cores + 1), `--timeout` and `--graceful-timeout`. Also try the `gthread` worker type.

<span id="concept-11-5"></span>

### <span class="concept-badge">11.5</span> Uvicorn

An ASGI server on an event loop (the model from [4.8](/part-4-raw-servers/#concept-4-8)). In production run several worker processes, either via its `--workers` flag or under Gunicorn with the Uvicorn worker class.

<span id="concept-11-6"></span>

### <span class="concept-badge">11.6</span> Why nginx in front

Sync workers are expensive: a slow client holding one ties up a whole process. nginx's buffering ([8.5](/part-8-reverse-proxy/#concept-8-5)) absorbs slow clients so workers finish in milliseconds.

<span id="concept-11-7"></span>

### <span class="concept-badge">11.7</span> Unix sockets vs TCP

Bind the app server to `unix:/run/gunicorn.sock` on the same host, or to `127.0.0.1:8000`. Never expose it publicly.

<span id="concept-11-8"></span>

### <span class="concept-badge">11.8</span> Static and media files

Let nginx serve `/static/` directly with `alias`. Django's `collectstatic` gathers them into one folder for this.

<span id="concept-11-9"></span>

### <span class="concept-badge">11.9</span> Trusting proxy headers

The app must know it is behind HTTPS. Django uses `SECURE_PROXY_SSL_HEADER`; Flask uses Werkzeug's `ProxyFix`; Uvicorn has `--forwarded-allow-ips`. Misconfiguring this breaks redirects or opens spoofing holes.

<span id="concept-11-10"></span>

### <span class="concept-badge">11.10</span> Other ecosystems

The same pattern everywhere: Node (Express or Fastify, often behind nginx), PHP (PHP-FPM via `fastcgi_pass`), Java (Tomcat or Netty), Go (its `net/http` is production-ready by itself, but nginx still adds value in front).

## The Java side: Tomcat, Jetty, Netty and virtual threads

The Java world has the same layers with different names. Once you map them, everything in this part applies.

| Python | Java equivalent | Used by |
| --- | --- | --- |
| WSGI (sync interface) | Servlet API (Jakarta EE) | Spring MVC, most classic Java web apps |
| ASGI (async interface) | Reactive handlers on Netty | Spring WebFlux, Vert.x, Quarkus reactive |
| Gunicorn (worker pool) | Tomcat or Jetty (thread pool) | Spring Boot embeds Tomcat by default |
| Uvicorn (event loop) | Netty (event loop) | WebFlux, gRPC Java, many API gateways |
| Django, Flask | Spring Boot, Quarkus, Micronaut | Your application code |

### The servers to know

<span id="concept-11-11"></span>

### <span class="concept-badge">11.11</span> Tomcat

The default in Spring Boot. Its NIO connector is a hybrid: a poller watches every open connection with epoll (up to `max-connections`, default 8192), then hands ready requests to a worker pool (`server.tomcat.threads.max`, default 200). `accept-count` (default 100) is the listen backlog from [1.8](/part-1-networking/#concept-1-8).

<span id="concept-11-12"></span>

### <span class="concept-badge">11.12</span> Jetty

The same hybrid idea, very embeddable. Spring Boot's alternative starter.

<span id="concept-11-13"></span>

### <span class="concept-badge">11.13</span> Netty

A pure event loop, the same model as nginx ([4.8](/part-4-raw-servers/#concept-4-8)). Fast and memory-efficient, but your code must never block the loop.

<span id="concept-11-14"></span>

### <span class="concept-badge">11.14</span> Undertow

Was the third Spring Boot option, but [Spring Boot 4 dropped it](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide) because Undertow doesn't yet support the required Servlet 6.1 baseline. You'll still meet it in older Spring Boot 3 services.

<span id="concept-11-15"></span>

### <span class="concept-badge">11.15</span> Virtual threads (Java 21+)

Set `spring.threads.virtual.enabled=true` and each request gets its own cheap JVM-managed thread. A request blocked on I/O parks its virtual thread and frees the OS thread underneath.

With Tomcat, the 200-thread cap then stops mattering, and `max-connections` becomes the real limit. They help I/O-bound apps, not CPU-bound ones.

### Spring Boot behind nginx: the settings that matter

- `server.address=127.0.0.1` so only nginx can reach port 8080.
- `server.forward-headers-strategy=native` so Tomcat trusts `X-Forwarded-For` and `X-Forwarded-Proto` from nginx (the Java version of [11.9](#concept-11-9)). Without it, redirects point to `http://` and logs show nginx's IP.
- `server.shutdown=graceful` so a deploy finishes in-flight requests ([4.12](/part-4-raw-servers/#concept-4-12)).
- Why nginx still helps: Tomcat's poller handles slow request headers well, but writing a large response to a slow client still ties up a platform worker thread. nginx's buffering, TLS termination and static files take that load off the JVM.
- A classic Java 502: the JVM is still warming up, or paused in garbage collection, when nginx connects. Watch for it after every deploy.

### Java lab

(one sandbox)

1. Build a Spring Boot app with a `/slow` endpoint that sleeps 2 seconds, and put nginx in front.
2. Load test with `wrk -c400`. With 200 platform threads, latency roughly doubles once more than 200 requests are in flight.
3. Set `spring.threads.virtual.enabled=true`, rerun and compare.
4. Run `jcmd <pid> Thread.print` during the test and count the `http-nio` worker threads in each mode.
5. Log `request.getRemoteAddr()` with and without `forward-headers-strategy` and see the real client IP appear.
6. Set `server.tomcat.accept-count=1`, flood the app, and watch `ListenOverflows` climb with `nstat` (field guide, TCP drops step 2).

## In the sandbox

1. Write a WSGI app as one bare function with no framework. Run it with Gunicorn. This shows how thin the interface really is.
2. Do the same with a raw ASGI function under Uvicorn.
3. Deploy a small Django app: Gunicorn on a Unix socket, nginx in front serving `/static/`, TLS from Part 5, systemd units from Part 2.
4. Add a slow endpoint (sleeps 2 seconds). Load test sync Gunicorn, Gunicorn with `gthread`, and Uvicorn. Compare throughput.
5. Remove nginx and point a slow-client script directly at Gunicorn's sync workers. Watch it freeze.
